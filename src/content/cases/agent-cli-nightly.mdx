## 手動更新の滞留と破壊的変更

日常の開発環境では、外部のコーディング CLI（コマンドライン上で動く開発支援ツール）を 3 本併用しています。対象は Claude Code、Codex、もう 1 つの CLI です。こうしたツールは更新間隔が短く、機能の追加や修正、挙動の変更が高頻度で入ります。気づいたときに手動で更新する運用では、忙しい時期に更新が滞り、複数の変更がまとめて手元へ流れ込みがちでした。

まとめて更新した直後に動きが変わると、どの変更が原因かを追いにくくなります。日中の実装を止めて更新と動作確認へ移る手間も重く、先送りするほど未適用の差分が膨らむ悪循環に入っていました。

加えて、本体側には上流（開発元の標準版）へ入っていない自前パッチを 1 本当てています。本体を更新するたびに、この差分が衝突せず再適用できるかを確かめる必要がありました。手動では確認が抜けやすいため、毎晩 1 回の定期更新と更新直後の健全性確認へ移すことが課題になりました。

## 更新運用の前提と制約

夜間の自動更新を組むにあたり、制約が 3 つありました。1 つ目は、本体と外部 CLI 群の更新を同じ時刻に重ねないことです。同時に書き換えると、翌朝に異常が見つかった際、本体の変更と CLI 側の変更のどちらが原因かを切り分けにくくなります。時刻とログの区切りを離し、異常の起きた段を追える形にする必要がありました。

2 つ目は、上流に入っていない自前パッチ 1 本の整合性を毎回の更新で機械的に判定することです。上流のコードが進んでパッチの当て先が変わったり、差分がずれたまま見過ごされたりすると、必要な挙動が黙って消えます。毎朝の目視確認では続かないため、再適用できるかを自動判定する仕組みが要りました。

3 つ目は、検査と公開前チェックの責務を曖昧にしないことです。更新処理が通っても、起動失敗や設定崩れは実際に動かすまで分かりません。あわせて、記録や成果物を外へ出す場面では、秘密情報や個人パスが混ざるおそれがあります。何が検査され、何が対象外かを明確に分けることが前提になりました。

毎晩 1 回の実行で通る手順は次の 4 段です。

- 03:00 に本体を更新し、上流の最新状態を取り込む
- 上流にない自前パッチ 1 本の逆適用チェック（更新後のコードへパッチを衝突なく再適用できるかの検証）を実行する
- 1 時間後の 04:00 に Claude Code・Codex・もう 1 つの CLI を順に更新する
- 更新後にスモークテストを流し、各 CLI の更新の有無と成否を記録する

本体を 03:00、CLI 群を 04:00 と 1 時間ずらしたのは、両者の境界を時刻とログで明確に保つためです。03:00 の本体更新とパッチ検証が終わってから 04:00 の CLI 群更新が始まるため、異常の出た段をログの時系列だけで切り分けられます。深夜帯に寄せているので、日中の作業中に CLI の挙動が切り替わる事態も避けられます。

自前パッチ 1 本に対して毎晩 1 回の逆適用チェックを挟んでいるのは、上流の変更でパッチが静かに効かなくなる状態を防ぐためです。更新後のコードと食い違えばその晩のうちに検知できるため、原因が 1 日分の差分に収まった状態で手当てできます。複数日分の変更が重なってから衝突を解く場合と比べ、修正箇所をすぐ特定できます。

更新後のスモークテストでは、更新処理が通った各 CLI が実際に動作できる状態かを確かめます。更新が 1 本も入らなかった晩も含めて記録を残し、どの晩にどのツールが書き換わって検査を通ったのかを後から辿れるようにしました。

また、成果物を公開する前段には成果物ゲート（公開前の生成物を自動検査して基準外の出力を止める関所）を置いています。このゲートが担うのは、署名やハッシュの検証ではなく、秘密情報と個人パスの漏れを検出する検査です。環境固有のパスや認証情報の混入を機械的に止める役割に限っており、署名検証やハッシュ照合とは明確に分けて運用しています。

## 記録 23 回分の更新実績

毎晩 1 回の実行を積み上げた記録 23 回分の実績を見ると、外部 CLI の更新頻度の高さが表れています。23 回分のうち、更新が入った回数は Claude Code が 16 回、Codex が 9 回、もう 1 つの CLI が 17 回でした。3 本を合計すると 23 回分で延べ 42 件の更新があり、1 回の夜間実行あたり平均 1.8 件ほどの CLI が書き換わった計算になります。

23 回の実行に対する更新の割合は、Claude Code が 16 回、もう 1 つの CLI が 17 回、Codex が 9 回です。1 回の実行あたりに直すと、多い 2 本は約 0.7 回、Codex は約 0.4 回になります。合計が延べ 42 件になるため、1 晩で複数の CLI が書き換わることもあります。

この記録 23 回分（延べ 42 件の CLI 更新）を通じて、更新処理やスモークテストの失敗は 0 件でした。ロールバック（異常時に直前の動作状態へ切り戻す手順）の実施も 0 件です。毎晩 03:00 の本体更新に伴う自前パッチ 1 本の逆適用チェックも、23 回分すべてで再適用不能は起きていません。

毎晩 1 回の更新と検査が途切れず通ったことで、日中の作業開始時には常に 1 晩分の差分だけが反映された状態を保てています。まとめて更新していた時期のように、いつ入った変更で挙動が変わったのかを遡る手間はなくなりました。

## 継続運用で得た知見

記録 23 回分で延べ 42 件、1 回あたり平均 1.8 件という更新量は、手動追従が滞りやすかった背景をそのまま表しています。更新が数回分溜まるだけで複数ツールにまたがる差分が一気に重なるため、1 晩ごとに刻んで取り込む設計にしておくと影響範囲を小さく保てます。

一方で、記録 23 回分のあいだ失敗 0 件・ロールバック 0 件で推移した事実は安全性の証明にはなりません。障害が起きていない裏返しとして、ロールバック手順そのものは実運用の失敗時に一度も通っていない状態です。スモークテストで拾えるのは最低限の起動と基本動作の破損までで、実際の開発作業で現れる細かな仕様変更までは覆いきれません。0 件という結果は「現状の検査網に引っかかる壊れ方がまだ起きていない」と読むのが正確です。

本体側の自前パッチを 1 本にとどめている点も、毎晩の自動更新を回せた理由の 1 つです。上流にない差分が増えるほど衝突確率は上がり、逆適用チェックで止まったときの解消コストも膨らみます。自前の変更を 1 本に絞って毎晩の検証へ組み込んだからこそ、上流へ追従しながら差分を保てています。

公開前の成果物ゲートについても、検査対象を秘密情報と個人パスの漏れに限定して明示しておくことが判断の助けになりました。ゲートを通過した事実だけを見て署名やハッシュまで検証済みだと取り違えると、改ざん確認という別の論点を見落とします。各チェックの保証範囲を分けて把握しておくと、運用上の盲点が残りにくくなります。
