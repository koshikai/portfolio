## 未圧縮と見えた 12 会話と計測の取り違え

会話の圧縮状況を監視していたところ、閾値を超えているのに未圧縮と見える会話が 12 件並んでいました。しかし、設定やコードへ手を入れる前にログと計測記録を突き合わせた結果、圧縮の仕組み自体は壊れておらず、悪く見えた数字は計測対象の取り違えによるものでした。原因を確かめたうえで、今回は設定もコードも変えずに確認を終えています。

長い会話を扱うエージェント運用では、会話が一定の閾値を超えた段階で履歴を要約して圧縮する LCM（Lossless Context Management）を動かしています。監視の集計で、閾値を超えた会話が未圧縮のまま 12 件残っているように見えれば、圧縮処理が止まっている、あるいは閾値の設定やトークンの数え方に誤りがあると疑いやすい状況です。

異常らしき数値が並んだとき、そのまま閾値の設定を書き換えたり、圧縮処理のコードへ修正を入れたりすると、正常に動いている処理へ不要な変更を加えることになります。今回の確認で課題になったのは、未圧縮と見えた 12 会話が本当に本会話の圧縮漏れなのか、それとも計測側の要因で数字が悪く見えているだけなのかを、設定変更の前にログと記録から切り分けることでした。

## 集計対象と監視指標の前提

監視の数字を正しく読むには、どの指標を見ているのかという計測基準と、どの会話が集計へ入っているのかという母集団の前提を押さえる必要がありました。

指標の面では、圧縮の実行を決める閾値判定と、状態を追うモニタはどちらも同じ量を見ています。対象は、キャッシュ分を含めた入力トークン数である `prompt_tokens` です。本体側とモニタ側で別々のトークン定義を参照していれば、閾値を超えていない会話が超過扱いに見えたり、超過している会話を見落としたりする食い違いが起きます。今回の構成では、閾値判定とモニタの双方がキャッシュ込みの `prompt_tokens` を基準にしており、数え方の前提は揃っていました。

一方で、運用環境にある会話の種類と記録の扱いには違いがありました。保存対象となる本会話のほかに、バックグラウンドで動くレビュー用の fork 会話が存在します。このレビュー用 fork はホスト側で圧縮を切っており、圧縮を無効のままにしていることがログへ記録されます。

集計に影響していたのは、telemetry（稼働状況やトークン数などの計測記録）の扱いです。レビュー用 fork はホスト側で圧縮を切っている状態であっても、telemetry には fork の会話 ID で記録が残っていました。そのため、会話の種類を分けずに telemetry を集計すると、圧縮対象の本会話と、圧縮を切っているレビュー用 fork が同じ一覧へ混ざる状態になっていました。

加えて、要約に使うモデルの切り替えも前提としてありました。11-16〜23 の期間は主力の軽量モデルで要約を行っており、11-24 に要約経路を Claude Haiku へ切り替えています。記録を読む際は、この切り替え前後の時期を分けて見る必要がありました。

最初に、閾値判定とモニタが同じ量を参照しているかを照合しました。片方がキャッシュを除いたトークン数を見ていて、もう片方がキャッシュ込みの値を数えていれば、圧縮処理に異常がなくても監視上は閾値超過に見えます。双方の基準を確認したところ、どちらもキャッシュ込みの `prompt_tokens` を見ていました。

次に、閾値を超えたのに未圧縮と見えていた 12 会話について、個別の会話 ID をログと突き合わせました。12 会話それぞれが保存されている本会話なのか、バックグラウンドのレビュー用 fork なのかを個別に確認しました。ホスト側のログに出力される `keeping compression DISABLED on this review fork` の行と telemetry の会話 ID を対応付け、集計へ混入していた対象を特定しました。

あわせて、fork を除いた本会話そのものが圧縮されているかを実行履歴から裏付けました。保存されている本会話のうち閾値を超えて未圧縮のまま残っている件数を調べ、11-20〜26 の期間における圧縮の開始回数と完了回数を照合しています。さらに、11-16〜23 の軽量モデル時代と 11-24 に Claude Haiku へ切り替えた後のログ・利用記録を時期別に切り分け、過去の失敗と現在の稼働状態を分けて確認しました。

## 本会話の稼働実績と過去の要約失敗

ログと計測記録を突き合わせた結果、閾値を超えたのに未圧縮と見えた 12 会話は、すべてバックグラウンドのレビュー用 fork でした。いずれの会話もホスト側で圧縮を切っており、ログには `keeping compression DISABLED on this review fork` の行が残っています。圧縮を無効にした会話が fork の会話 ID で telemetry に記録され、そのまま集計へ混ざっていたため、監視上で未圧縮が 12 件あるように見えていました。

保存されている本会話に絞って確認したところ、閾値を超えて未圧縮の状態にあるものは 0 件でした。11-20〜26 の期間における本会話の圧縮は、開始 27 回に対して完了も 27 回です。閾値判定とモニタがどちらもキャッシュ込みの `prompt_tokens` を見ていることも確認できており、指標の食い違いはありませんでした。本会話に対する圧縮は止まらずに動いていました。

一方で、時期をさかのぼって記録を確認すると、本当の失敗は別の時期に起きていました。11-16〜23 の期間は要約モデルが主力の軽量モデルで、1 回の要約に約 100 秒かかって時間予算を使い切っていました。加えて、生成された出力が元より長い場合や、出力の中身が空になった場合に拒否される事象も発生していました。

11-24 に要約経路を Claude Haiku へ切り替えてからは状況が変わっています。切り替え以後、LCM の警告は 0 行で推移しており、要約ノード 6 件がすべて公開されています。利用記録である `session_model_usage` でも、11-25 に `task=compression` として Haiku が 6 回呼び出されていることを確認しました。

実チャンクに対する圧縮実績も記録に残っています。実チャンク 16,189 トークンを 15.2 秒で 1,618 トークンまで圧縮しており、元のトークン数に対して約 1/10 の分量に収まりました。

以上の確認により、監視上で未圧縮と見えた 12 会話は fork の混入による見かけ上の集計結果であり、保存されている本会話の圧縮も Haiku 切り替え後の要約経路も壊れていないと確定しました。そのため、今回は設定もコードも変えていません。

## 監視数値の読み方から得た学び

監視の数字が悪く見えたとき、設定やコードへ手を入れる前にまず確かめるべきなのは「何を数えているか」でした。

今回起きていたのは、閾値判定とモニタで「数え方が違う」のではなく「対象が違う」問題でした。同じキャッシュ込みの `prompt_tokens` を見ていても、集計の母集団に「ホスト側で圧縮を切っている会話」が混ざっていれば、未圧縮の会話が滞留しているように見えます。指標の定義が一致していることを確認しただけでは、未圧縮に見える原因は解けません。どの会話 ID が telemetry に記録されているかまで母集団を確かめて初めて、12 会話がすべて fork であり、本会話の未圧縮は 0 件だという実態が分かりました。

仮に「未圧縮が 12 会話ある」という数字だけを根拠にして閾値を調整したり、圧縮処理のコードを書き換えたりしていれば、壊れていない本会話の挙動へ不要な変更を加えるところでした。圧縮を切っているログ行と会話 ID を突き合わせた結果、設定もコードも変えないという判断が取れています。

あわせて、見かけの数字と過去の失敗を時期で切り分ける点も運用の学びになりました。11-16〜23 の失敗は 11-24 の要約モデル切り替えで解消しており、いま集計に見えている 12 会話とは別の出来事です。時期ごとの記録を混ぜずに並べ直すことで、すでに解消した失敗と現在の集計上の誤読を切り離せました。

## 集計の読み分けと今後の確認方針

今回の確認では設定もコードも変えていないため、レビュー用 fork がホスト側で圧縮を切られたまま fork の会話 ID で telemetry に記録される構造は残っています。会話の種類を分けずに telemetry を集計すれば、今後もレビュー用 fork の分だけ閾値超過かつ未圧縮として数えられる状態が続きます。

今後の運用では、監視の集計に異常らしく見える数字が出た際、設定やコードを疑う前に「どの会話 ID が集計対象に入っているか」を最初に確かめる手順を基本にします。未圧縮として計上された会話が、圧縮を有効にしている本会話なのか、ホスト側で圧縮を切っているレビュー用 fork なのかを先に切り分ければ、見かけの件数だけで不要な変更へ進まずに済みます。

あわせて、telemetry の集計を読み取る側でも、本会話と圧縮を切っている fork を分けて確認する見方を維持します。保存されている本会話については、閾値を超えて未圧縮のものが 0 件であるかと、対象期間の開始回数と完了回数が一致しているかを基準に確認を続けます。Claude Haiku の要約経路でも、LCM の警告が 0 行のままで推移しているか、`session_model_usage` の `task=compression` 記録と要約ノードの公開が揃っているかを継続して見ていく方針です。
