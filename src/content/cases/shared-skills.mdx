## スキルの分散と未使用ファイルの滞留

Hermes Agent を複数のプロファイル（用途ごとに状態や設定を分ける作業単位）で動かしていると、定型作業の手順をまとめたスキル（エージェントが参照する手順書）の置き場所が問題になります。プロファイルごとに個別のディレクトリへ置いたまま運用すると同じ手順が別々の場所へ散らばり、片方を直しても別のプロファイルへ反映されず、どの時点の内容を参照しているのかも追えなくなります。

全プロファイルから参照できる 1 か所の git 管理ディレクトリへ集約した直後にも、別の課題が出ました。2026-11-16 に運用を始めた時点で、上流（公式の配布元や外部の提供元）から取り込んだ分を含めて 66 本のスキルが並んでいました。あらかじめ手順書を揃えておけば対応できる作業が広がるように見えますが、実際には一度も使われないファイルがそのまま残ります。プロファイル側で必要な手順を選ぶ際の見通しが悪くなり、候補が増えるほど点検の手間もかさみます。

この記事で扱うのは、スキルを増やすのではなく使うものだけに絞る運用への切り替えと、共有ディレクトリを設けたあとでも同名のローカルコピーが残ると共有側が無視される罠の解消です。

## 読み込みの優先順位と集計の罠

共有ディレクトリを 1 か所に置くだけでは、全プロファイルが常に同じ手順書を読む状態にはなりません。運用を設計するうえで制約になったのは、読み込みの優先順位、退避ディレクトリの数え方、上流との同期状態の 3 点です。

まず押さえる必要があるのは、スキル読み込みの優先順位です。Hermes Agent は、作業対象のリポジトリ側（`project`）、プロファイル固有の配置先（`local`）、全プロファイルから参照する共有ディレクトリ（`external`）の順に、3 段階でスキルを探します。優先順位は `project` > `local` > `external` であり、上位の層に同じ名前のスキルが見つかると、下位の層は参照されません。

この仕様のため、`external` に最新の共有スキルを置いていても、プロファイル側の `local` に同じ名前のコピーが残っていると共有側が無視されます。エラーは出ず、古いコピーがそのまま使われ続けるため、共有側を直しても動作が変わらない原因に気づきにくくなります。エージェント自身がスキルを書き換える運用では更新先の食い違いも起きるため、有効な重複を 0 件に保つ制約がかかる形です。

もう 1 つの制約は、外したスキルの数え方です。すぐ消さずに `.archive`（稼働対象から外したファイルを退避するディレクトリ）へ移す運用では、ディレクトリ配下を素朴に数えると退避済みまで混ざります。その結果、実際に稼働している本数に対して、見かけの本数が 1 回の集計で 2〜4 倍に膨らみます。退避済みを混ぜた数字では棚卸しの進捗を正しく読めません。

上流由来のスキルを扱う場面では、管理情報との整合性も外せません。本体ファイルだけを移動したり削ったりすると、上流との対応を記録する lock（導入元との同期状態を保持する管理情報）が実体と食い違います。本体を消したあとに取り残される孤立した lock や、放置された上流の更新待ちを溜めない点も、継続運用の条件になります。

導入にあたって最初に行ったのは、本数の削減です。2026-11-16 に 66 本で共有ディレクトリを立ち上げた当日、一度も使われていない上流由来の 27 本（開始時 66 本の約 4 割）を稼働領域から外し、39 本まで絞りました。2026-11-26 時点では 38 本です。外したファイルは即座に削除せず `.archive` へ退避し、参照や復元が必要になっても元の記述を確認できる状態を残しました。

共有ディレクトリ自体は git で管理し、エージェントが書き換えた分を毎晩 02:15（1 日 1 回）に自動でコミットする仕組みを入れました。作業の中でエージェントが手順書を修正しても、その日のうちに差分が履歴へ入ります。変更がない日は何もしない設定のため、意味のない空コミットは積み上がりません。人の手で整理した変更とエージェントによる追記の両方が同じ履歴に並ぶので、意図とずれた修正が入った場合でも差分を見て戻せます。

日々の維持では、優先順位の罠と集計の誤りを防ぐため、次の手順で点検しています。

- `external` と同名のコピーが `local` に残っていないか確かめ、有効な重複を 0 件に保つ
- `hermes skills check` を実行し、1 回の点検で上流の更新待ちと孤立した lock が 0 件であることを確認する
- 有効なスキル数を数えるときは `.archive` 配下を外し、稼働中のファイルだけを対象にする
- 毎晩 02:15 の自動コミットで入った差分を読み、特定プロファイルだけの前提が共有側へ混ざっていないか確認する

## 66 本から 38 本への推移と稼働状況

共有ディレクトリの本数は、2026-11-16 の開始時点の 66 本から、同日の棚卸しで未使用の上流由来 27 本を外して 39 本になり、2026-11-26 時点で 38 本です。開始時の 66 本から 28 本減り、残存は約 58% です。

git 履歴には、2026-11-16 から 11-26 の 11 日間で 17 件のコミットが入りました（1 日あたり約 1.5 件）。毎晩 02:15 の自動コミットは変更がなければ動かないため、実際に書き換えや整理が起きた分だけが履歴として残ります。エージェントが手順を更新した日も自動でコミットが作られ、手作業の記録は不要になりました。

整合性の確認では、2026-11-26 時点で有効な重複が 0 件でした。`local` 側に同名コピーを置かないルールを守ったことで、共有側を更新したのに古いコピーが読み込まれる事態は起きていません。あわせて `hermes skills check` の 1 回の確認でも、上流の更新待ちは 0 件、孤立した lock も 0 件でした。集計から `.archive` を外したことで、1 回の集計で生じる 2〜4 倍の膨らみにも惑わされず、稼働中の 38 本をそのまま把握できています。

## 共有運用で確かめた判断基準

11 日間の運用を通して分かったのは、手順を増やす工夫より、使わないものを外す基準と重複を防ぐ確認のほうが共有ディレクトリの保守に直結することでした。

開始当日の 66 本のうち 27 本は、一度も使われていないという事実だけで外せました。上流からまとめて取り込んだ手順書は、いつか使うかもしれないという理由で残りがちですが、稼働実績のないファイルが並ぶとプロファイル側で必要なスキルを選ぶ判断が遅くなります。実際に使う見込みが立った段階で取り込む形にしておけば、共有ディレクトリ全体の見通しを保ちやすくなります。

読み込みの優先順位（`project` > `local` > `external`）は作業リポジトリごとの上書きを許す合理的な仕組みですが、共有運用へ移ったあとに `local` へ同名コピーが残ると、エラーも出ないまま共有側が無視されます。優先順位の挙動を前提に「有効な重複を 0 件に保つ」と基準を置いたことで、版違いの混入を防げました。

集計の面でも同じ注意が要ります。`.archive` に移す運用は、誤って消した手順を戻せる利点がある一方、ディレクトリ全体を素朴に数えると 1 回の集計で見かけの本数が 2〜4 倍に膨らみます。本数の増減を運用の目安にするなら、数える対象から退避領域を外す定義まで決めておくべきです。

## 今後の手入れ

現在の 38 本は 2026-11-16 から 11-26 の 11 日間で絞り込んだ構成ですが、運用が長くなれば使われなくなる手順書は再び出てきます。開始当日に 27 本を外した棚卸しを 1 回きりで終わらせず、一定期間ごとに利用実績を見直し、参照されなくなったスキルを `.archive` へ移す手順を続けます。

毎晩 02:15 の自動コミットは変更を履歴へ残すところまでを担い、複数プロファイルで共有してよい内容かまでは判定しません。履歴がまとまった時点で差分を見直し、共有に適さない前提が紛れ込んでいないかを確かめます。

あわせて、`local` 側への同名コピーの混入を 0 件に保つ確認と、`hermes skills check` で確認する上流の更新待ち・孤立した lock の 0 件維持を継続します。
